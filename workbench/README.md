# Security Architecture Review & Threat Modeling Workbench

An internal, browser-based workbench for cybersecurity consultants and security architects. You import an existing diagram or draw the architecture, confirm it into a versioned canonical model, threat-model it (STRIDE, PASTA, OCTAVE), review it against approved control catalogs (NCA ECC, SAMA CSF, NIST CSF, ISO/IEC 27001), manage risks on a 5×5 matrix, and generate DOCX, PDF and Excel reports.

> **Demonstration build.** By default the server runs in a *demonstration* environment with synthetic sample data, demo control-catalog excerpts and external AI services disabled. Do not load client data until a production-approved environment is configured (see [Production configuration](#production-configuration)).

## Quick start

```bash
cd workbench
npm install
npm run dev          # API on :4310, UI on http://localhost:5173
```

On first start the server creates demo accounts `admin`, `lead`, `analyst` and `viewer`, and writes their shared password to `server/data/DEMO_CREDENTIALS.txt`. To choose the password yourself, set `SAWB_DEMO_PASSWORD` before the first start.

To run a production build on one port:

```bash
npm run build
SAWB_SECURE_COOKIES=false npm start     # http://127.0.0.1:4310. Omit the variable when serving over HTTPS.
```

Tests:

```bash
npm test             # unit tests (engine, Draw.io import, controls, reports, crypto) + API integration tests
npm run typecheck
```

## Modules

| Module | What it does |
|---|---|
| **1. Project management** | Assessments with client alias, scope, client architecture version, reviewer, status workflow (draft → in review → pending approval → final → archived) and review date. Per-project history, project audit trail, member management, and draft copies cloned from existing assessments. |
| **2. Architecture editor** | SVG drag-and-drop editor: 11 component types, labelled data flows (protocol, port, encryption, authentication, classification), trust zones with trust levels, and per-type security properties recorded as yes / no / unknown. Autosave, undo, zoom and fit. Versions are immutable, SHA-256-hashed snapshots of the canonical JSON model (`sawb.architecture/1.0`), with comparison and restore. JSON export and import. |
| **Imports** | Structured **Draw.io** import (compressed or plain XML, containers become zones, keyword-based type inference shown per element). **PDF and image** diagrams are uploaded as evidence and transcribed manually with page or location references. Everything imported lands in a **confirmation queue** as *unconfirmed*, and unconfirmed elements are never analysed. |
| **3. Threat modelling** | A server-side deterministic rule engine applies STRIDE per element, PASTA attack paths (entry points → critical assets over confirmed flows) and OCTAVE Allegro areas of concern. Each item records affected assets, category, attack scenario, preconditions, existing controls, missing information, likelihood, impact, rating, mitigation, rationale and the exact model facts it relied on. Results are split into **confirmed findings**, **hypotheses** and **missing evidence**. Analysts accept or reject items, add notes and evidence references, and can add their own threats. Re-runs keep their decisions. |
| **4. Control review** | Versioned catalogs are imported as drafts and approved by a *different* user. Only approved versions can be used. Findings map to controls by topic tags, and missing information is flagged per control. A control can only be marked "Evidence reviewed — satisfied" when an evidence reference is attached. Compliance is never inferred from the diagram. |
| **5. Risk register** | Configurable 5×5 matrix (labels and bands) with an inherent/residual heatmap. Each risk has an owner, treatment strategy and status, target date and mitigation actions. Reviewer approval enforces segregation of duties (the registrar cannot approve, and an owner is required). Material edits return a risk to pending. |
| **6. Reporting** | Security Architecture Review, Threat Model, Risk Register and Remediation Roadmap. Generated by backend services (`docx`, `pdfkit`, `exceljs`) from one document structure, which also drives the in-browser preview. Reports include the architecture snapshot, executive summary, methodology, findings, risk ratings, evidence references, limitations and recommendations. |

## Security controls implemented

* **Authentication.** scrypt password hashes, a password policy, forced change on first sign-in after creation or reset, and a 15-minute lockout after 5 failures.
* **Sessions.** Random tokens in an `HttpOnly`, `SameSite=Strict` cookie (`Secure` in production), with idle and absolute timeouts. A double-submit CSRF token is required on every state-changing request.
* **Authorisation.** Global roles (administrator, lead reviewer, analyst, viewer) are combined with **project-level membership** (owner, editor, viewer). Every API route checks both. Archived assessments are read-only.
* **Audit trail.** Append-only and SHA-256 hash-chained, with integrity verification in the UI. It covers sign-ins and failures, every change, evidence access, approvals, AI requests and exports.
* **Encryption at rest.** The data store and every evidence file use AES-256-GCM with purpose-bound AAD. The key comes from `SAWB_DATA_KEY`.
* **Secure file handling.** Size limit, extension allow-list *and* magic-byte verification, sanitised filenames, SHA-256 integrity check on retrieval, `Content-Security-Policy: sandbox` on served evidence, and no-store caching. In the demonstration environment each upload requires a synthetic-data attestation.
* **HTTP hardening.** CSP, `X-Frame-Options`, `nosniff`, a referrer policy, HSTS in production, and no stack traces in API errors.

## AI services: the interface only, not operational

`server/ai.ts` defines the `AiAdapter` interface (document extraction and analysis) and an empty adapter registry. **No AI provider adapter ships with this build**, and the UI reports the services as *not operational*. Even after an adapter is added, a document is sent only when **all** of these hold:

1. `SAWB_ENV=production` (a production-approved environment);
2. `SAWB_AI_PROVIDER` and `SAWB_AI_ENDPOINT` are configured, and a matching adapter is registered;
3. `SAWB_AI_ALLOW_DOCUMENTS=true`;
4. a lead reviewer approved that specific document; and
5. the requesting user confirmed that individual request.

AI output may only add *hypotheses* or *unconfirmed* model elements for analyst review.

## Production configuration

| Variable | Purpose |
|---|---|
| `SAWB_ENV=production` | Disables demo seeding and demo content, and allows AI approvals. |
| `SAWB_DATA_KEY` | 64 hex characters (32-byte AES key). **Required** in production. Keep it in a secrets manager. |
| `SAWB_BOOTSTRAP_ADMIN_PASSWORD` | Initial administrator password (production first start only). |
| `SAWB_DATA_DIR` | Location of the encrypted store and evidence files. |
| `SAWB_MAX_UPLOAD_MB`, `SAWB_SESSION_IDLE_MINUTES`, `SAWB_SESSION_MAX_HOURS` | Limits. |
| `SAWB_AI_PROVIDER`, `SAWB_AI_ENDPOINT`, `SAWB_AI_ALLOW_DOCUMENTS` | AI interface gating (see above). |

In production no control catalogs are pre-loaded. An administrator imports the firm-approved catalog JSON (format shown in the UI) and a lead reviewer approves it.

## Demonstration content

* The sample assessment *Online Banking Portal (DEMO)* is **synthetic**. Its threats come from running the real engine over the synthetic model; nothing is hard-coded. Two elements are deliberately left unconfirmed to show that unconfirmed elements are excluded from analysis.
* The demo catalogs are **short, paraphrased, domain-level excerpts** marked "demo excerpt". They are not authoritative control text.

## Known limitations and next steps

* Persistence is a single encrypted JSON document, which suits a small team. For multi-user scale, move to a database with row-level project scoping and per-tenant keys.
* Sessions are held in memory, so a restart signs everyone out. SSO (SAML/OIDC) and MFA are not built in yet.
* Draw.io import reads the first page only. PDF and image diagrams require manual transcription until an approved AI adapter is added.
* Rule-engine rules are intentionally conservative. Extend `COMPONENT_RULES` in `shared/engine.ts` to add organisation-specific threat patterns.

## Component library and framework register

**Component library.** The architecture editor's palette includes a searchable library of 2,549 components in 24 groups (cloud services, network devices, identity, data stores, third parties and others). Clicking an item adds it to the canvas, with its name kept as `catalogRef`. Each item gets a default model type from its group, which the Inspector can change. The library is served to signed-in users at `GET /api/catalog/components`. Its data, provenance and licensing notes are in `catalog/README.md`. The vendor icons are included for internal use only, as agreed. 309 Azure entries have no icon in the source material and show a generated tile.

**Framework register.** `shared/frameworks.ts` lists the 18 sources you asked for, with role, version, official source, licence status and the stated scope where you gave one. The Control catalogs page shows the register. The register holds no control text. Each framework's version and source must be confirmed against the publisher before import. Licensed texts (ISO/IEC 27001 Annex A, SABSA, TOGAF, CIS) are imported through the versioned catalog import, where a different reviewer must approve them before use.

**Not yet integrated from the ArchGuard prototype:** its heuristic review and STRIDE engine, its standalone canvas and editing screens, and its JSON/SVG/CSV exports. The workbench already has its own canvas, JSON export and report exports. The workbench's deterministic engine is the analysis source of truth. The prototype's checks are not used.

## Architecture editor (ArchGuard designer)

The **Architecture** page hosts the ArchGuard prototype editor (`client/public/designer/`). It replaces the original editor. It saves to the project's architecture model through the same API as the Architecture page. The threat analysis, versions and reports read that model.

- A small bridge (`designer/bridge.js`) replaces the prototype's `localStorage` calls. The workbench sends the model in, and the bridge posts changes back.
- `shared/designer.ts` converts between the two models. Designer-only fields are stored with a `designer.` prefix, so a round trip loses nothing. Analyst-entered fields the designer does not show are kept on save.
- The designer is framed on the same origin only. All other pages still refuse framing.

Versions (save, compare, restore), JSON export and JSON import are on the same page. Changes restored or imported from elsewhere reload the editor with the new model.

The STRIDE, PASTA and OCTAVE engine is kept, alongside the PROTOTYPE method described below.

## PROTOTYPE analysis method (Phase 2)

The **PROTOTYPE** method ports the ArchGuard prototype's rule checks into the workbench engine (`shared/prototype-rules.ts`). New projects use it by default. It can be combined with STRIDE, PASTA and OCTAVE.

Changes from the prototype, to meet the workbench's rules:
- Only confirmed components and flows are checked.
- An explicit "no" gives a confirmed finding. An unknown value gives a missing-evidence item. Generic scenarios are hypotheses.
- Prototype control mappings (for example "NIST SP 800-53") are kept only as unverified references in each rationale. They are not approved control content.
- Likelihood and impact come from the prototype's severity. The mapping is a default in `SEVERITY_RATING`, to be confirmed by the analyst team.

Projects created before this change keep their existing methods. Select PROTOTYPE in the project settings to use it.
